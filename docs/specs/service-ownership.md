# Service ownership

## Purpose

Engwire uses one launchd label per macOS user, while `ENGWIRE_HOME` lets one user keep several installations. Every command that reports on that job, replaces it, or removes it therefore has to answer a question first: is this job mine? Getting it wrong in either direction is expensive — stopping somebody else's runner mid-review, or deleting the data a running service is still reviewing from.

## Scope

Governs how Engwire identifies the launchd job it may act on, and what `service install`, `doctor` and `uninstall` each do with that answer. Covers macOS only; launchd is the only supervisor Engwire implements.

Does not otherwise cover what the runner does once started ([architecture.md](../architecture.md)), or how the binary reaches the machine ([releases.md](releases.md)).

## Requirements

**One label, one job.** Engwire installs under `com.engwire.local` in the user's launchd domain. That is fixed, so Engwire's launchd integration supervises at most one installation per macOS user, regardless of how many exist on disk. It bounds what Engwire installs, not what a person can start: `engwire run` under any other supervisor is outside it.

**A service must still mean what it meant once the installing shell is gone.** The plist carries path settings verbatim and preserves no working directory, so a relative value has no settled meaning between the preflight and the service. `service install` therefore refuses relative or empty values for Engwire's bases and for `GH_CONFIG_DIR` and `CLAUDE_CONFIG_DIR`; it also refuses an environment that names no data directory, which would produce a service Engwire immediately reads as foreign. `uninstall` refuses a confirmed run over relative roots rather than deleting trees whose locations depend on the caller's working directory. Foreground `engwire run` also rejects relative installation paths and a relative effective gh configuration root. A relative Claude root holds reviews at skill preflight. `doctor` reports these problems; service installation checks the environment destined for the plist rather than the caller’s shell. See [architecture.md](../architecture.md) for command guards.

**An installation is its data directory, not its spelling.** The queue, runner lock and worktrees all key on that directory, so two environments that resolve to it are the same installation however their config roots differ. Paths are compared as written first and through the filesystem second, resolving the deepest part `realpath` can follow: `/tmp` is a symlink to `/private/tmp`, and `service install` can record a different spelling from the one `uninstall` later reads. The data directory need not still exist, so a surviving symlinked ancestor must be enough to establish identity. Deletion asks a different question: a removal root that is itself a symlink is unlinked and reported, never followed, because its target may be moved Engwire data or an unrelated directory. The lock is the exception because `acquireLock` follows links; a data root pointing inside the config tree puts `runner.lock` there, so removal is refused rather than allowed to delete the pathname it is holding. Resolving stops short of one case, and the entry answers instead: a `runner.lock` that is itself a symlink can put the lock outside the pathname model removal is built on, and resolving cannot say where while the target does not exist yet — so a confirmed run refuses. Removal roots may be symlinks; the lock pathname may not.

**The plist is the record; launchd holds the job.** The two can disagree. `install` replaces the file before booting out the old job, so the file can be ahead; deleting the file by hand leaves a job loaded with nothing describing it, so the file can be absent while the job runs. Engwire reads the file for identity and asks launchd only for the one question a file cannot answer — whether a job is loaded when no plist is there.

**Identity comes from the plist's own environment.** A plist is Engwire's if it carries the fixed label, names an absolute executable, has the generated document shape, and its environment resolves to the asking installation's data directory. Both ends of that meet in the middle. The generator writes a carriage return as a character reference, because XML turns a literal one into a line feed before anything reads it — the preflight would otherwise approve one directory and the service run against another. The file is then turned into what an XML processor would receive — decoded as UTF-8 or refused, line ends normalised, comments taken out only where a comment may go — so that this reader and launchd cannot disagree about what the document says.

Anything else is somebody else's. The file itself: unreadable, bytes that are not the encoding declared, or text XML cannot hold. The document: comments anywhere but between elements, a root dictionary carrying anything but the pairs the generator writes — truncation and stray markup land here — or a name or value spelled some way the generator would not have, an entity left to decode being the one that matters, since launchd's XML reader resolves it and Engwire's recognizer does not. And the job it describes: a root key this version has no meaning for, or a known key written as a kind this version does not write it as. That last pair is why a name is not enough — a plist can name this installation in its environment and still describe a different job, and the only keys Engwire can weigh are the ones it writes, in the kinds it writes them. Repeating one of the three keys ownership turns on, or a variable inside the environment, ends the answer too: the document is disagreeing with itself, and which half launchd would honour is not measured.

**Unidentifiable is somebody else's, never nobody's.** The job on the other end may be a runner in the middle of a review. `engwire service uninstall` remains the one command that removes the user's job without asking whose it is; nothing else stops a job it can see is not its own.

**Ownership is answered, not held.** The answer comes from a file, while `launchctl bootout` names only the shared label, so another installation can replace the job between the answer and the act. Removal re-reads the plist immediately before bootout and declines whenever this installation can no longer claim it. That narrows but does not close the race; only a lock shared across installations could do that, and Engwire does not serialize interactive service commands. A declined run deletes nothing because the ambiguous cases require opposite actions: another installation holding the label leaves this one's data safe to remove, while a vanished plist may have left this installation's job loaded. The next run reads the service fresh and distinguishes them.

## Failure behavior

`service install` refuses a setup the background runner could not use — a source checkout, a failing preflight, an account the queue does not belong to — and says so rather than installing a service that would fail quietly. When it does replace a job it could not claim, it says that too, describing the plist it found rather than the job it displaced: another install could replace that job before this one reaches `launchctl`.

`doctor` reports a foreign plist without failing on it. The row says which installation it supervises, or that it does not say; neither is this installation being unhealthy.

`uninstall` removes only a job it can claim, and only when confirmed: the plain invocation lists and removes nothing. A job that can no longer be claimed when the bootout comes — taken by another installation, or left with no plist at all — is left alone and reported as such, rather than counted as removed. A foreign or unidentifiable job is listed as kept, and a confirmed run that completes closes by naming `engwire service uninstall`. Kept, not stopped, and not reported as running either: a plist is a file, and launchd is asked about the job only when no plist describes one. The data and configuration go with a confirmed run too — they belong to the installation being removed whoever owns the job, and a job left kept is no reason to keep them. The failed revalidation above is the one exception: there the run ends with everything still in place. When the kept job could be this installation's own — any orphan, or a plist that cannot name the installation it supervises — a successful removal says it may start a runner here again. That possibility is a sentence, not a veto: it does not stop a job whose ownership Engwire cannot establish, and it does not keep the data of an installation somebody asked to remove.

`uninstall` refuses a confirmed run when its two removal roots are one tree, one contains the other, or the data root reaches into the config tree through a link — ancestors resolved for the first two, since a link above a root is followed and one at a root is not; fully resolved for the third, which asks where the lock is rather than what removal reaches. The independent XDG bases allow all three and `ENGWIRE_HOME` allows none. When either root exists, the plain invocation remains non-destructive and describes the shape it would refuse. `uninstall` takes the runner lock rather than probing it, so a foreground runner cannot start between the check and deletion, and removes configuration before data. A held transaction outlives its file but not its pathname, so the data root containing that pathname goes last; configuration goes first because a runner that cannot read it never reaches the lock. The runner meets this from the other side by reading configuration before taking the lock and again under it; only the second read authorizes work. A data root that is a regular file or dangling link cannot hold a lock and is removed last so it remains a barrier until then. A held lock stops removal before either root is deleted. If the claimed service was already stopped, it cannot restart the runner; an unidentifiable job may do so and is named; an identified foreign job supervises another data directory and is not blamed for this lock. Off macOS no launchd job is claimed, and Engwire makes no promise about an external supervisor.

None of the identity checks may throw. `service install` asks them, and it is the command someone runs when the installed service is the thing that is wrong.

## Verification

`launchd.test.ts` covers identification from generated, hand-edited and hostile plists, including a data directory reached through a symlink and a path that cannot be resolved. `uninstall.test.ts` covers every ownership answer with the runner stopped, each answer that changes what a held lock reports, relative roots, a lock reached through a link, and all three entangled layouts. Engwire's reading of `launchctl print` is a pure rule with its own test, so the measured codes are pinned where they are used. `doctor.test.ts` covers the reported rows, and `service.test.ts` covers replacement notices and invalid service path settings.

The launchd behaviour these rest on is measured in [experiments.md](../experiments.md): `launchctl print` exits 0 for a loaded label and 113 for one the domain does not have, which is a different code from the one `bootout` uses for the same absence.
